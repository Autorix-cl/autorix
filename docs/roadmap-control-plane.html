Ground truth, before any planning

This roadmap starts from an audit of the actual repository, not from the existing docs/roadmap.md — which declares the project "100% COMPLETADO" including liveness probes and observability. Each finding below was verified by reading the code and running the stack. A second audit re-ran on 2026-08-18 against the current working tree — findings still open are unchanged below; the one that got fixed is marked so, not deleted, per this doc's own "never fake a signal" principle.

What this means for sequencing

Four consequences drive the phase order. First, nothing can be tracked before engines can honestly answer "am I alive", so the health contract precedes the registry. Second, the registry is the backbone every other surface hangs from, so it lands immediately after — but headless, as an API. Third, the console must gain no management power while still unauthenticated, so identity comes before any management screen, including the fleet's own. Fourth, screens are built once: the design system precedes every screen that would otherwise be hand-rolled and rebuilt.

That last pair is why registration splits across two phases. The backend lands in Phase 2 and is verifiable with curl; its console surface lands in Phase 5, on an authenticated console with a design system underneath it. The alternative — shipping fleet screens in Phase 2 — would put enrollment-token minting and instance eviction on an open port, and would build tables and forms that Phase 4 immediately replaces. The full picture is in the dependency graph.

The centerpiece: engines that register themselves

The requirement is that starting an engine is what puts it under management. That implies a component none of the seven engines can play: something already running, that outlives any individual engine, and that no engine sits in the request path of. This roadmap introduces it as an eighth service.

Autorix Argus — the control plane

Named for Argus Panoptes, the hundred-eyed watchman, and following the suite's existing convention. A new Go module github.com/autorix/argus, built to the same hexagonal layout as its siblings (internal/core, internal/transport, internal/storage/postgres), with its own database autorix_argus, REST on :4400 and gRPC on :50053.

Why a separate service rather than logic inside the console. Registration must succeed when nobody has the console open, and must survive the console being redeployed. The console is a stateless UI; making it the registry would put fleet state in the presentation tier and force it to be permanently online. Argus is also the natural single source of truth for the CLI, Terraform provider and public API in Phase 9. The alternative — engines writing to a shared table — was rejected because it reintroduces the shared database that this architecture's entire premise rejects.

Why push rather than pull. A console-side scanner cannot find engines it was never told about, which is exactly the case the requirement describes: an operator brings up an engine and expects it to appear. Self-registration also lets the engine advertise what a scanner cannot infer — build SHA, schema version, feature capabilities, its own view of its dependencies. Operator-initiated manual registration remains supported as a fallback for engines that cannot be given an enrollment token.

The enrollment handshake

1

Operator mints an enrollment token

In the console, scoped to an engine type and environment, with a TTL and a single- or multi-use policy. The console shows ready-to-paste snippets for Docker, Helm and a bare binary.

2

Engine boots holding the token

Passed as AUTORIX_ENROLLMENT_TOKEN alongside AUTORIX_ARGUS_URL, AUTORIX_ENVIRONMENT and an optional AUTORIX_INSTANCE_ID. Absent these, the engine runs exactly as it does today — unregistered but fully functional.

3

Engine calls POST /v1/register

Advertising engine type, semantic version, build SHA, schema version, its REST and gRPC endpoints, declared capabilities and declared dependencies. Argus validates the token against its type and environment scope.

4

Argus issues an instance credential

A long-lived, rotatable per-instance secret replacing the one-shot enrollment token. Subsequent calls are authenticated with it; heartbeats carry an HMAC signature. In production, mTLS is layered on top.

5

Engine heartbeats every 15 seconds

Carrying liveness, readiness, dependency reachability and lightweight counters. The client library retries with jittered backoff and — critically — never blocks or fails the engine's own request serving.

6

Engine deregisters on SIGTERM

A graceful goodbye distinguishes a planned shutdown from a crash, so the console can show "stopped by operator" rather than raising an incident. Instances that vanish without it are reaped on a timer.

Instance lifecycle

pending→ registering→ healthy→ degraded→ unreachable→ evicted · deregistered

healthy means readiness passes and heartbeats are current. Two missed beats moves an instance to degraded; four to unreachable; twenty-four hours without contact evicts it from the active fleet while retaining its history. deregistered is reached only through the graceful path and is never an alert.

The rule that keeps Argus safe

Argus is never in the data path. If Argus is down, every engine keeps authenticating, authorizing and proxying exactly as before — the registration client degrades to buffering heartbeats and retrying. The console loses fleet visibility, nothing else. This constraint is tested explicitly, because a control plane that can take down the data plane is worse than no control plane.

What changes inside the seven engines

Each engine gains a dependency on a new shared module github.com/autorix/platform providing the health contract, structured logging, metrics and the registry client. In main.go this is roughly ten lines: construct the client, start it, defer graceful deregistration. Every engine keeps its independence — the module is a library, not a runtime coupling, and an engine with no Argus configured behaves as it does today.

Principles

Never fake a signal

A surface that reports health must report real health or say it does not know. "Unknown" is a valid, useful state; a hardcoded "healthy" is a liability. This principle exists because the codebase currently violates it.

The control plane is optional

Every engine runs standalone with no Argus, no console and no siblings. Registration adds management; it never becomes a startup dependency.

Degrade by feature, not by page

With three of seven engines registered, the console shows three working sections and honest "not connected" states for the rest — never a broken page, never invented data.

Dogfood, with a way out

The console secures itself with Ego, Janus and Nexus once they are available, and keeps a break-glass local admin so the system is recoverable when they are not.

Backend work is roadmap work

Most missing console features are missing because the engine API does not exist. Those tasks are specified here as Go work, not hand-waved as UI.

Every mutation is attributable

Who, what, when, before, after — recorded for every state change from the day authentication ships, not retrofitted before an audit.

The UI is not the only client

Console features are built on a versioned control-plane API that the CLI, Terraform provider and customer automation consume identically.

What can run in parallel

With more than one engineer, the safe parallelism is inside phases rather than across them. Phase 6 splits cleanly by engine — seven independent tracks, one per service, once Phases 4 and 5 are done. Phase 7's instrumentation work can begin alongside Phase 6 as soon as Phase 1's middleware exists, since it touches different code paths. Phases 1 through 3 are the serial spine: almost everything depends on them, and running them concurrently mostly produces rework.

One exception worth taking early. P9-S3-T1 fixes the Go SDK's Check(), which currently returns true without contacting Nexus. If any deployment relies on it for authorization today, that is a live security defect and should be fixed immediately rather than waiting for Phase 9.

Argus — Registration Backend

The stated requirement, working end to end at the API layer: bringing an engine up registers it, and from that moment it is inventoried, heartbeated, versioned and related to its dependencies. Deliberately headless — the console surface for it ships in Phase 5, after the console can authenticate an operator and has a design system to build on.

Exit criteria

  • Starting any engine with an enrollment token registers it within one heartbeat interval, with version, endpoints and capabilities — verifiable with curl against the fleet API, no UI required.
  • Stopping it gracefully records "stopped by operator"; killing it moves it through degraded to unreachable on the documented timers.
  • Killing Argus itself changes nothing about engine behaviour — proven by an automated test that asserts full data-plane function with the control plane down.
  • The fleet API answers correctly for an arbitrary subset of registered engines, including none at all.

Why no screens in this phase. Enrollment tokens are the credential that admits an engine into your fleet, and force-remove evicts a running instance. Shipping those controls on a console that still has no authentication — which is the state until Phase 3 — would hand fleet control to anyone who can reach port 3000. That is strictly worse than today, so the UI waits.

Decisions that need you

Each of these changes the shape of the work, and none should be decided by the implementer by default.

Q1Is Argus the right answer, or should the registry live inside an existing engine?

This roadmap adds an eighth service. The alternative is folding the registry into the console's backend, which is simpler to ship but couples fleet state to the UI's lifecycle and leaves no control plane for the CLI and Terraform provider to talk to. The recommendation is the separate service; the cost is one more thing to deploy and operate.

Q2How much should the console dogfood Autorix for its own authentication?

Full dogfooding is the most persuasive demonstration the product can make, and it is also a circular dependency that complicates recovery. The roadmap proposes dogfooding with a permanent break-glass path. The alternative — the console keeping its own independent identity system — is safer operationally and weaker as a proof.

Q3Should Aegis move to Postgres?

It is currently the only engine without a database, storing rules in a YAML file. File storage cannot support multiple Aegis replicas, which makes it the one engine that cannot scale horizontally. Migrating aligns the architecture and unblocks HA; keeping the file is simpler and preserves GitOps-style rule management.

Q4What is the tenancy model, and when does it land?

Only Themis has a tenant concept. Retrofitting tenancy across six engines in Phase 8 is a large migration. If Autorix will be multi-tenant, doing this earlier is dramatically cheaper — the decision needs making now even if the work happens later.

Q5Do the engines' admin APIs get closed, and what breaks?

Every engine's admin surface is currently unauthenticated. Closing it is necessary but will break any existing integration that relies on open access. This needs a migration window and a decision about backward compatibility.

Q6Which observability stack?

The repository already assumes Prometheus and Grafana. Committing to that means the console embeds or links to Grafana rather than rebuilding charts; committing to OpenTelemetry end-to-end opens vendor choice. The roadmap assumes Prometheus with OTel tracing, but the console-versus-Grafana boundary should be decided before Phase 7 begins.

Q7Is the Go SDK's behaviour a live incident?

Check() returns true without contacting Nexus. If any deployment currently depends on it for authorization decisions, that is a live security issue rather than a Phase 9 task, and it should be fixed immediately regardless of this roadmap's sequencing.

Q8What is the team size and target date?

The sequencing assumes each phase is largely serialised. With multiple engineers, Phase 6 splits into seven independent tracks by engine, and Phase 7's instrumentation can run alongside it. Phases 1 through 3 are the serial spine and should not be parallelised away — see the dependency graph for what is genuinely concurrent.
